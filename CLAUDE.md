# Meal Planner

A weekly meal-planning system for one household (size, serving count, and tastes are in `profile/preferences.md` — plan one shared menu scaled to that household, never separate menus per person). Claude is the engine: it proposes meals, builds grocery lists, and maintains all records. The user's role is limited to approving/rejecting proposals, logging what got cooked, and rating meals.

**The primary interface is the app in `app/`** (Express + Claude Agent SDK on the Claude Code login, always-on via LaunchAgent) — see "The app" below. The slash commands remain the desktop fallback and the reference definition of each workflow. Setup steps for a new install are in `README.md`.

## User goals
1. Eat healthier
2. Eliminate the friction of recipe hunting and shopping-list creation
3. Keep track of everything (meals, ratings, nutrition, history)

## Weekly cadence

| Step | Command | What happens |
|------|---------|--------------|
| 1. Plan | `/plan-week` | Claude proposes the week's meals; user approves/rejects/swaps until the plan is locked |
| 2. Shop | `/grocery-list` | Claude generates the shopping list from the approved plan, split by store |
| 2b. Pictures | `/recipe-images` | After the list is final: a picture for every recipe that has none (ChatGPT via Chrome, one chat per image). Never part of lock; shopping doesn't need it. Also the **last step after any one-off recipe addition** (import, Ask Claude, hand-written) |
| 3. Log | `/log-meal` | User reports what actually got cooked + a 1–5 rating |
| 4. Review | `/review-week` | Claude closes out the week: updates recipe stats, notes patterns, feeds insights into next week's plan |

In the app, each step is a surface instead of a command: **Next tab** = plan (propose → per-meal approve/reject/swap → revise → lock, which also builds the grocery list), **Shop tab** = the list with live-shared checkboxes, **day cards** = log (stars/notes, folded to the record by a background run), **Week tab** = close out. Commands remain the desktop fallback for all four.

## Directory layout

- `profile/preferences.md` — household, tastes, restrictions, nutrition goals, logistics, stores (source of truth)
- `profile/pantry.md` — staples on hand; used to subtract items from grocery lists
- `profile/ideas.md` — batches of dish ideas written by the app's `ideas` run (created on first use)
- `recipes/` — one markdown file per recipe with frontmatter (nutrition, rating, times cooked); `recipes/README.md` is the format reference
- `plans/` — one file per week, named `YYYY-Wnn.md` (e.g. `2027-W03.md`); holds the plan, the grocery list, and the cooked log for that week
- `plans/TEMPLATE.md` — structure for weekly plan files
- `starter-recipes/` — a sample library shipped with the template. **Not the household's recipes**: never read it when planning, cooking, or answering; the Recipes tab's Starter library card copies chosen files into `recipes/` (and each one's picture from `starter-recipes/images/` into `recipes/images/`), and the folder can be deleted once it has served its purpose.
- `app/` — the app (server, UI, run prompts, selftest, LaunchAgent)
- `app/scripts/fixtures/` — synthetic sample files for the selftest. **Not history** — never read them as past weeks or as the recipe library.

## Rules for Claude

**Planning**
- Read `profile/preferences.md`, `profile/pantry.md`, and the last 2–3 weeks of `plans/` before proposing anything.
- Never propose anything on the hard-no / allergy list. Respect nutrition targets in preferences.
- Balance repeats and novelty: favor recipes rated 4–5, retire anything rated ≤2, and include new recipes at the rate set in preferences.
- Don't repeat a recipe within the minimum-gap window set in preferences. Check the **protein-level gaps** too — they bind across different recipes sharing a protein, so a new shrimp dish still violates a shrimp gap.
- Every proposed meal includes: active cooking time, and estimated nutrition per serving (calories, protein, carbs, fat, fiber). Active time **includes mise en place, for one cook doing everything, rounded up to 5 min**: the recipe's `active_time_min` (time rules in `recipes/README.md`), and the weeknight cap in preferences applies to that number.
- Prep is first-class: recipes declare `prep_ahead` (thaw/marinate/start-by) in frontmatter; locking a plan generates its Prep timeline with each task dated to the day it's **due**, not the day it pays off. The app surfaces prep as checkboxes on the day cards.
- Present proposals for approval one week at a time; iterate until the user locks the plan. Record rejections and why (rejection reasons are preference signals — fold recurring ones into preferences.md).

**Shopping**
- The stores are named in `profile/preferences.md` → Shopping. The **primary store** gets everything it sensibly carries; the **secondary store** is only for items the primary doesn't carry (or carries only in impractical bulk for the household). With no secondary store, everything goes on one list.
- Each store is a `### {store name}` heading in the plan file's Grocery list, primary first, using the names from preferences consistently week to week.
- Subtract pantry staples from the list. Flag pantry items that are likely running low.
- Account for bulk pack sizes: when a recipe needs an item sold only in bulk, plan additional meals that week (or the next) that reuse it, or note the freezer plan.
- Organize each store's list by section (produce, meat, dairy, frozen, pantry).
- Recipe ingredient lines carry a source tag: `[1]` primary store, `[2]` secondary store, `[P]` pantry (legend in `recipes/README.md`). Pack sizes and buying notes go inside the tag.
- Lists are built from **pre-scaled ingredient lines**: each meal's servings live in the plan's Servings column (default 4; set per meal with the Next tab's stepper), the app scales the recipe's Ingredients to it deterministically (`app/server/scale.ts`) and hands those lines to the lock/rescale runs. Aggregate them; never re-derive quantities. Source tags state pack sizes at base scale, so compute pack counts from the scaled amount. Scaling a locked meal is the Next tab's servings control (a light `rescale` run), never a hand edit or a recipe Notes entry.

**Tracking**
- Ratings are 1–5: 5 = make it weekly, 4 = regular rotation, 3 = fine, 2 = don't repeat soon, 1 = never again.
- After logging, update the recipe file's frontmatter: `rating` (running average), `times_cooked`, `last_cooked`.
- The weekly plan file is the historical record — never rewrite past weeks except to fill in logs.
- A night that wasn't cooked is logged `skipped — <reason>` in Actually cooked (the app's "Didn't cook" reasons: leftovers, ate out, no time, or free text); no rating, no recipe stats change.
- "Took about N min" (the app's took-about chips) goes into the Log note as a `(took ~N min)` prefix; close-out nudges that recipe's `active_time_min` toward it (average with the current estimate, round to 5) and says so in the review.
- New recipes get a file in `recipes/` when they're first approved into a plan, not before. Write them at `servings: 4` in the scalable format in `recipes/README.md`: every ingredient line starts with its quantity and unit (digits, not words); equivalents and pack counts go in the source tag, never in parentheses; a total that matters is the lead amount (`4 salmon fillets, ~6 oz each` or `1½ lb salmon`, never `1½ lb …, 4 × 6 oz`); an ` — ` breakdown sums to the lead; steps name ingredients rather than amounts; scaled variants never go in Notes. Every new file also gets a `description: "…"` line right after `name:` (one double-quoted sentence, ≤ 160 characters, on what the dish is and how it eats; no logistics, ratings, times or names; the Week tab's day cards show it instead of the planner's rationale, which stays on the Next tab), a `## Prep` section between Ingredients and Steps (the whole mise en place as `- ` bullets, `**Component:**` labels, ingredient names not amounts; Steps assume it's done) and `prep_min` right after `total_time_min`, with all three times set per the README's time rules.

**Sync (more than one device!)**
- This repo is used from more than one place: the always-on Mac that runs the app AND any other Claude Code session (another computer, or Claude Code web/mobile on a phone) working against the same private GitHub repo. Divergence is the failure mode.
- **Start of every session: `git pull` before reading or changing state.**
- After any state-changing step (plan locked, grocery list written, meals logged, week reviewed, preferences/pantry updated): commit with a descriptive message and push immediately. Don't batch several days of changes.
- If a push is rejected, pull --rebase and push again; conflicts in plan files resolve in favor of whichever side has the logged data.

**The app (`app/`)** — the primary interface (architecture overview: `SPEC.md`; install: `README.md`)
- Express + `@anthropic-ai/claude-agent-sdk` on the user's Claude Code login (no API key), WS live updates, vanilla JS frontend. **Always-on** via LaunchAgent `com.mealplanner.app` (template in `app/launchd/`; `app/launchd/install.sh` renders it with this checkout's path and installs it in `~/Library/LaunchAgents/`; it sources nvm because launchd has a bare environment). Logs: `~/Library/Logs/meal-planner.log`. Port 4316. On the Mac: `http://localhost:4316` · phone on home Wi-Fi: `http://<mac-hostname>.local:4316` · anywhere, if Tailscale is set up: `http://<mac-hostname>.<tailnet-name>.ts.net:4316`.
- **HTTPS + PWA** (optional): `https://<mac-hostname>.<tailnet-name>.ts.net` via `tailscale serve --bg 4316` (TLS ends in Tailscale; `trust proxy` = loopback, so `auth.ts` reads `X-Forwarded-For`/`Tailscale-User-Login` only from the local hop); the http URLs stay as the LAN fallback. Only an https origin can install the app to a phone's home screen, get Web Push (Settings → This phone; `app/server/push.README.md`), and receive Android shares (`POST /share` → `app/data/uploads/` + `shares.json`, then `/?shared=<id>`).
- **Restart after server changes** with `app/launchd/install.sh restart` (= `launchctl kickstart -k gui/$UID/com.mealplanner.app`) — but ALWAYS `GET /api/run` first and wait for `active: false`: run state is in-memory, a restart kills an in-flight run (the script refuses while a run is active). Captures/checks are persisted JSON and survive. Never `npm start` alongside the agent (port conflict); the repo's `.claude/launch.json` "meal-app" config only attaches a preview to the running server. Verify changes with `npm run typecheck` + `npm run selftest` (parsers checked against the sample files in `app/scripts/fixtures/`). The Agent SDK is **pinned** in `app/package.json` (never `"latest"` — a floated SDK version once broke git inside runs); after pulling app changes, `npm ci` in `app/` before restarting. Run git/read-tool permissions are granted via `allowedTools` rules (enforced CLI-side) with `canUseTool` as the deny-by-default backstop, so runs survive a broken SDK control channel.
- **Five tabs: Week · Cook · Recipes · Next · Shop** — Week/Recipes = the week being cooked, Next/Shop = the week ahead, Cook = at the stove. All computed live: the flip to a new week and the dashed carry cards for unlogged stragglers come from date + plan-status logic. Header retitles per tab. The UI persists view state (active tab, expanded recipes, per-tab scroll, cook dish + chat) in sessionStorage and restores it on boot, so a phone screen-lock reload lands back on the exact view.
- **Get started card** (Week tab, new installs): shown while the profile still has `_fill in_` placeholders or no plan exists — fill in the profile (opens Ask Claude with the interview request), import starter recipes (optional), propose the first week. The propose run is refused with a plain message until the profile is filled in.
- **Week tab · Trends card** (bottom of the tab): the last 12 locked/complete weeks as inline-SVG small multiples — calories and protein per serving over the dinners actually cooked (recipe `nutrition_per_serving`, else the plan row's estimate), nights cooked vs planned (cooked / skipped / not logged), average rating, protein lanes (chicken · fish · plant · red meat) — computed by pure `server/trends.ts` and served at `GET /api/trends` (open); the close-out prompt gets the same numbers through review.md's `{{TRENDS}}` (summary line + 6-week table), so the review's nutrition paragraph uses them instead of estimating.
- **Week tab · Kitchen window** (top of the Week tab only, above the header; `public/js/05-window.js` + the `.window` block in `style.css`): a drawn window over the sink showing the real sky, weather, time of day, season and moon for the household's place. One inline SVG, CSS animations on transform/opacity only (clouds drift with the wind, rain, snow, a storm flash), paused while the page is hidden and static under reduced motion. Weather is fetched **server-side only** by `server/weather.ts` from Open-Meteo (no key or account; 6 s timeout, 10-minute cache, last good snapshot served `stale` for up to 3 h, never throws) and served at `GET /api/weather` (open, 30/min) → `{ configured: false }` or the snapshot; the place comes from `GET /api/geocode?q=` (open, 20/min, up to 6 places; `server/weather-routes.ts`). Settings keys `location` (`{ name, admin1?, country?, lat, lon, tz }`, validated in `store.ts`; no built-in place — without one the window runs on the device clock with 07:00/18:30 and a clear sky) and `tempUnit` (`F`|`C`, env fallback `MEALAPP_TEMP_UNIT`, default F), set from the gear panel's **Kitchen window** section (place search → tap to save, °F/°C, and the per-device "Show the window" toggle in `localStorage mealapp-window`). The caption under the sill (`61° · light rain · <place>` · `sunset 6:40 pm`) opens that section. The client refreshes on Week-tab show, every 15 min while visible, on wake and on `settings-updated`; the scene math is pure and checked by `npm run selftest`. `?scene=<condition>-<phase>[-<month>][-<moon>]` (e.g. `rain-night`, `snow-day-jan`, `clear-night-full`) previews a scene, stripped from the URL like `?tab=`.
- **Week tab · Move a dinner** (`server/move.ts`, `weekMoveHtml` in `public/js/10-week.js`): a folded "Move" toggle beside "4 servings ▾" on tonight, Coming-up and unlogged Earlier cards of the **locked week being cooked** opens one chip per target (`Wed 14`, or `Thu 15 · swap with Red Lentil Soup`); tap → confirm → `POST /api/runs/move` `{ week, day, to }` (passcode) → the light `move` run. Eligibility is the pure `checkMove`, shipped per meal as `moveTo: [{ day, date, swapsWith? }]` in `/api/state` and re-checked by the endpoint: the source is a cook night not yet logged (no Log row with a rating or "Actually cooked", no capture with a rating or dish/skip); the target is another day of the week, today or later, not logged; a flexible target is a plain move, a target holding another unlogged dinner is a swap, and a dinner whose own day has passed may only move onto a flexible night. No control on flexible, carry or Next-tab cards.
- **Recipes tab** (library, sortable) with collapsed cards above it: **Starter library** (only while `starter-recipes/` holds recipes not yet in `recipes/`; importing copies the chosen files, plus each one's picture into `recipes/images/` unless one is already there, and commits them through `server/starter.ts`). **Ideas** = `profile/ideas.md`, written by an `ideas` run (plan model, passcode "New ideas" button): batches of 8 dishes not in the library, newest first, one `- **Name** · protein · cuisine · ~N min active — pitch. Why you: …` line each (format pinned in `server/ideas.ts` + `app/prompts/ideas.md`). **Queue** / **Not for me** (open, attributed) live in `app/data/ideas-state.json`; queued ideas reach the next propose as `{{QUEUED_IDEAS}}` until a plan carries them, dismissed + already-suggested + filed names reach the next ideas run as `{{IDEAS_STATE}}`. **Add a recipe** = an `import` run (plan model, passcode) from a pasted URL (fetched server-side, reduced to JSON-LD Recipe data or readable text, no model), a photo/PDF upload (`POST /api/imports/upload`, 15 MB, images/PDF only), or an Android **share** to the installed app (manifest `share_target` → `POST /share`); records in `app/data/imports/`. The run writes `recipes/<slug>.md` in house format (Prep section, honest times, nutrition at 4, `source:`, `times_cooked: 0`, never overwriting: `-2` suffix), appends a dated "user-supplied recipe" entry to Learned preferences, commits; the result card offers Open recipe + **Queue for next week**. Paywalled recipe sites can't be fetched server-side: share the PDF or screenshots instead.
- **Recipe images**: one picture per recipe at `recipes/images/<slug>.jpg` (slug = recipe filename minus `.md`; made per `recipes/images/README.md` by the desktop command `/recipe-images`: a manual ChatGPT-via-Chrome loop that runs **after** the lock/grocery list, or as the last step of a one-off recipe addition, never inside a run), found by filename, never by frontmatter. The app only reminds: `imagesMissing` in `/api/state`, a **Pictures to make** card on the Recipes tab, and a line on the lock and import result cards. Served at `/recipe-images/` (image files only, 1 h cache) and surfaced as `image` on `/api/recipes`, `/api/recipes/entry` meta and the `/api/state` meals (`repo.ts recipeImages`): a hero on Tonight and the Cook tab, a 56px thumb on day cards, Next and the Recipes list; no image, no slot.
- **Cook tab**: dish picker (defaults to tonight, explicit picks persist) + full recipe + **sous-chef chat**. Chat = `POST /api/cook/ask` (passcode, 10/min): streams from the cook model with the recipe + preferences + pantry embedded; read-only tools (Read/Grep/Glob in-repo), never git, **not a run** — usable while a run is active. Transcripts live client-side per recipe (sessionStorage, 40-msg cap); the server keeps no chat state. Built for the stove: servings stepper (1–24; defaults to the plan's servings for that meal, else as written) → `GET /api/recipes/entry?f=…&servings=N` returns `sections` (ingredients scaled by `server/scale.ts` via `server/recipe-sections.ts`, `## Prep`, steps, notes) + `scale`, with a "Scaled ×2 for 8" banner; a `## Prep` mise-en-place checklist and tap-to-mark current step (both per recipe + day); the sous-chef opens as a bottom sheet from a floating button (questions carry the servings, so answers are at the cook's scale); Screen Wake Lock while a recipe is open (pill toggle, needs the https:// address).
- **Ask Claude** (`server/ask.ts`, `public/js/80-ask.js`): a round chat button left of the gear on every tab opens a bottom sheet for the things that would otherwise need a desktop Claude Code session — ingredient substitutions, recipe modifications that stick, pantry and preference changes, questions about past weeks, and the first-run profile interview. `POST /api/ask` (passcode, 10/min) streams from the **plan** model with the whole repo readable and the **run tool gate** (writes inside the repo + plain git, `settingSources: ['project']`, max 30 turns); it may ask a clarifying question. It **holds the run lock** while answering (strip shows "Asking Claude", Stop aborts it, runs/auto-fold/git pull wait; refused with 409 "Claude is busy" while a run is active). Changes are committed + pushed like a run; a turn that changed files ends with `Changed: <paths>` plus a server `[git] pushed|committed|uncommitted` line, shown as chips, followed by `state-updated`. A dropped connection doesn't abort the turn (`GET /api/ask/last?turn=` refills it after a screen-lock reload). Transcript client-side (`sessionStorage`, 40 msgs); the server keeps no chat state.
- **The repo stays the only system of record.** The server *parses* `plans/` and `recipes/` (formats pinned by `plans/TEMPLATE.md` — don't drift them, the parser and `app/scripts/selftest.ts` bind them). What the parser depends on: the Plan table's exact columns (read by header text, `Servings` included), the `**Status:**` line starting with `planning` / `locked` / `complete`, `- [ ] **Ddd D, time:** task` prep lines, `### Store` / `**Section**` / `- [ ] item` grocery structure, the `### Pantry check` and `### Bulk notes` headings, the Log table's columns, and recipe frontmatter keys. The server never writes repo files, with two deterministic exceptions, both committed through `server/commit.ts` and refused with 409 while a run, chain or Ask Claude holds the run lock: the **Pantry sheet** (Shop tab → Pantry, or Settings) edits `profile/pantry.md` through `server/pantry.ts` (marker conventions in its header: `(added YYYY-MM-DD via app)`, ` ⚠️ low (YYYY-MM-DD)`, `- ~~…~~ — used YYYY-MM-DD (note)`), and the **Starter library** import copies files from `starter-recipes/` into `recipes/`. Otherwise agent runs are the only writers.
- **Capture → fold:** stars/notes/dish-corrections POST instantly to `app/data/captures.json` (gitignored, lives only on the Mac) keyed by ISO date; shared checkboxes (prep + shop, week-scoped keys) live in `checks.json` and sync over WS between devices. A **fold run** (light model) writes pending captures into the plan files' Log tables after ~5 min of quiet (delay + on/off in the gear panel; `MEALAPP_AUTOFOLD=off` is the env fallback) or via "Sync now"; entries get `foldedAt` stamped. `week-review` folds whatever is still pending itself, so closing a week is always safe.
- **Runs** (one at a time, tool-gated to writes-inside-repo + plain git, `settingSources: ['project']` so this file's rules bind): `propose` → `revise` (consumes per-meal ✓/✗/↻ feedback + week notes from the Next tab) → `lock` (recipe files for 🆕, prep timeline, grocery list, folds Shop-tab extras) → `fold` → `shop-adjust` → `review`, plus `ideas` and `import`, and two light one-meal edits of a locked week: `rescale` (servings) and `move` (a dinner to another day: the two Plan-table rows exchange everything but the Day cell, the `- **Day:**` planning bullet is relabeled and a `- **Moved (date, via app):**` bullet appended, that dinner's prep tasks are re-dated with their lead kept, tasks ticked in `checks.json` come in as `{{DONE_PREP}}` and stay byte-identical, a freshness task is added when the new day outlasts a fresh or thawing protein, and the Grocery list, Bulk notes and Log are never touched; on desktop a move is a hand edit following `app/prompts/move.md`). Prompts in `app/prompts/*.md` — they are the app-mode translations of the four commands and pin the exact file formats. Feedback/extras are cleared after the run that consumes them. Runs commit+push per the sync rules; the server `git pull --ff-only`s throttled on reads and never during a run. **Chains** (`startChain` in `runs.ts`: one lock across the steps, Stop ends the chain, a failed step stops it and says which step did not run): **close-and-plan** (Week tab: `review → propose`, with cook-night chips and constraints collected up front) and **send-and-lock** (Next tab: `revise → lock`, replacements auto-approved through revise.md's `{{AUTO_APPROVE}}` block, refused while any meal is undecided; "Approve all" fills decisions in one tap).
- **Trust model**: reachability is the identity — anyone who can reach the port (home network, or the tailnet if Tailscale is used) can use the app. GETs open; captures/checks/feedback/extras open but rate-limited, and attributed via `tailscale whois` when the request arrives over Tailscale (unattributed otherwise); run triggers, stop, deletes, Ask Claude, the pantry sheet and the starter import need the shared passcode (`x-mealapp-passcode`, stored per device). Passcode file: `app/data/passcode.txt` (gitignored) or env `MEALAPP_PASSCODE` — **with neither set the gate is off**, so set one at install; rotating the file needs no restart. Env: `MEALAPP_PORT`, `MEALAPP_MODEL` (plan/review runs), `MEALAPP_LIGHT_MODEL` (fold/adjust), `MEALAPP_COOK_MODEL` (default = light — sous-chef chat), `MEALAPP_PASSCODE`, `MEALAPP_AUTOFOLD`, `MEALAPP_PUSH_CONTACT` (the Web Push VAPID contact, `mailto:` or `https:`; defaults to the repo's git `user.email`).
- **Dev knobs** (dev instances on another port only, never the LaunchAgent): `MEALAPP_MOCK_RUNS=1` swaps every run's and Ask Claude's SDK call for canned events + summary (no Claude, no writes, no git), tuned by `MEALAPP_MOCK_MS` (per-step duration, default 4000) and `MEALAPP_MOCK_FAIL=<type>[,<type>]` (those run types fail); `MEALAPP_NO_GIT=1` = no git anywhere (real runs, Ask Claude, the pantry sheet and the starter import leave edits uncommitted; no boot or throttled pull); `MEALAPP_DATA_DIR=<dir>` = the instance's own state folder instead of `app/data/`; `MEALAPP_PUSH_DRYRUN=1` = Web Push notifications are logged, not sent, with `MEALAPP_PUSH_DRYRUN_TODAY=YYYY-MM-DD` standing in for today (`server/push.README.md`); `MEALAPP_WEATHER_FAKE=<json>` = the kitchen window's `/api/weather` returns that object merged over a plausible base snapshot (e.g. `'{"current":{"code":63,"cloudCover":95}}'`), no Open-Meteo call and no place needed (`server/weather.ts`). E.g. from `app/`: `MEALAPP_MOCK_RUNS=1 MEALAPP_NO_GIT=1 MEALAPP_PORT=4317 MEALAPP_DATA_DIR=<scratch dir> npm start`.
- **Settings (gear icon, header):** models + effort per tier (plan / light / sous-chef), auto-fold on/off + quiet delay, the Kitchen window's place and °F/°C, per-device passcode/theme/chat-clearing/window toggle, and a read-only Status block (gate, uptime, HEAD, SDK version, last git pull incl. errors, pending captures, typical run times). Server values persist in `app/data/settings.json` (gitignored; `GET` open, `PUT /api/settings` passcode) and **override env**: effective = settings.json > env > built-in. Changes apply to the next run/chat, no restart; `{}`/absent file = pure env behavior. **Push notifications** (This phone section, HTTPS origin only; sent by `app/server/notify.ts`): per-phone toggles for run-done (one per run or chain), record-updated, prep-today and tonight, plus the two daily times `pushPrepTime` (08:00) / `pushTonightTime` (16:30) as server settings.

**General**
- **Onboarding:** `profile/preferences.md` and `profile/pantry.md` ship as blank templates. While either still contains `_fill in_` placeholders, onboarding is not complete — don't propose a plan. In an interactive session (desktop Claude Code, or the app's Ask Claude chat), interview the user a few questions at a time and fill the files in, remove every placeholder and the "Blank template" note, then commit and push. In an app run (no interaction possible), change nothing and say in the final message that the profile needs to be filled in first. Once filled in, `profile/preferences.md` is the live source of truth.
- **Dates:** weeks run Saturday–Friday, named `YYYY-Wnn` by the ISO week of the Monday they contain (= the ISO week of date + 2 days for any date in the week); planning happens Friday, shopping Saturday morning (day 1 of the week). This scheme is hard-coded in the server (`app/server/weeks.ts`) and assumed by the UI's nudges, so changing the planning/shopping days means changing code, not just preferences. The same file carries legacy handling for week ids up to `2026-W32` (Monday-start weeks); it only matters to the selftest fixtures.
